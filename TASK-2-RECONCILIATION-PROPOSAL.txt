TASK 2 — RENDER-TIME PRESCRIPTION RECONCILIATION: DESIGN PROPOSAL
Branch: task-0-injury-profile
Status: PROPOSAL — reviewed with user, not yet implemented. No generator
code written against this yet.

================================================================================
GROUNDING — facts pulled from the actual code before writing this proposal
================================================================================

- The render pipeline has exactly one real assembly point in intent —
  DayPage (index.html:2487-2489): day.exercises.map(resolveSlot) +
  bonusForDay(...). But it is not the only place that pattern exists.
  weeklySetsByGroup (969), dayFittedMinutes (863), dayFocusSummary (2449),
  and DayPicker.lastDone (2393) each independently reconstruct the same
  list. This matters directly for item 3 below: patching DayPage alone
  leaves weeklySetsByGroup (which feeds Gate 6's baseline) computing the
  pre-reconciliation list, reintroducing double-counting by a different
  route. All five have to route through one function.

- sessionRules is currently a no-op. KNOWN_PLAN_KEYS (3805) does not
  include sessionRules — a pasted plan's sessionRules is stripped and
  reported as an "ignored field" before buildGateContext ever sees it. So
  today, weeklyGroupSetCaps / maxSetsPerMovement / trimPriority /
  orderByFocus are all inert regardless of what's pasted. This has to be
  part of Task 2's wiring, not a separate follow-up.

- Swaps (data.swaps) are keyed by base slot id, global to the account,
  independent of data.plan.prescriptions. No template-static day has two
  exercises sharing an id — verified by parsing PROGRAMS directly — so
  within the generator's own output, duplicates don't happen. They CAN
  happen if two different slots are independently user-swapped to the same
  replacement id (checked the swap code at 2617-2629: nothing prevents
  that convergence).

- Manual template switching (2335, 4286) already spreads ...plan and
  touches only template/templateSince — data.plan.prescriptions survives a
  template switch untouched today. No new "don't delete it" code is
  needed; the open question is only visibility.

- applyPasted replaces data.plan.prescriptions wholesale on every apply
  (3964) — it doesn't merge with what was there before. So there's no
  cross-paste layering to reason about, only within-batch collisions.

- Gate 8 (deload) currently bakes its scaling into the stored prescription
  at apply-time (gate8DeloadOverride, called inside
  applyGatedPrescriptions), while DayPage separately re-applies its own
  deload scaling to every rendered entry, unconditionally, based on deload
  state at render time (2491-2494). Once a prescription is one of the
  entries being rendered, that's two independent deload multipliers
  stacking on the same number. This is a real bug the reconciliation work
  surfaces, not a hypothetical — flagged as an open decision below, since
  fixing it touches signed-off Task 4 behavior.

================================================================================
1. ONE SHARED RESOLVER, NOT FIVE DUPLICATED CALL SITES
================================================================================

New function (name TBD — resolveDayExercises(day, data)), replacing the
"day.exercises.map(resolveSlot) + bonusForDay" pattern everywhere it
currently appears: DayPage, weeklySetsByGroup, dayFittedMinutes,
dayFocusSummary, DayPicker.lastDone. In order:

  1. day.exercises.map(slot => resolveSlot(slot, data.swaps, focus)) —
     generator + swaps, exactly as today.
  2. + bonusForDay(day, focus, program) — exactly as today.
  3. NEW STEP: reconcile against data.plan.prescriptions filtered to this
     day (see section 2).
  4. Return the list. Deload scaling and fitDayToTime stay OUTSIDE this
     function, applied by each caller as needed (some callers, like
     dayFocusSummary, don't want the deload-scaled numbers).

This is the change that makes "keep the baseline honest" true by
construction rather than by convention: weeklySetsByGroup and DayPage read
the SAME list, so there's no route left for them to disagree.

================================================================================
2. REPLACE-VS-ADD — DEFAULT TO REPLACE (per user's directive)
================================================================================

Rationale: add-by-default silently reintroduces the exact volume-stacking
failure this build started from.

Matching rule: a prescription's exerciseId matches an existing slot in
that day if it equals the RESOLVED (post-swap, step 1-2 above) .id of an
entry already in that day's list — not the pre-swap slot id. This single
rule is what answers question 4 for free (below). If it matches -> replace
in place (splice the merged entry into that array index, never push a
second one). If it doesn't match anything in that day -> add (push a new
entry); the full gate stack runs on it exactly as it does on a replace.

dayKey is required on every prescription, not optional. The spec's example
fills it in on every entry, and it's an identity field (which day) rather
than an override parameter (sets/reps/load, which ARE legitimately
omittable). It's also load-bearing for ADD — without it there's no way to
know which day gets the new exercise. Treating exerciseId + dayKey + order
as required identity fields; sets/repMin/repMax/load/restSec stay optional
partial overrides per the spec.

================================================================================
3. THE SIX QUESTIONS
================================================================================

Q1 — Can an exerciseId appear twice in one day's output?
Checked directly: no template's static day list has a duplicate id. It CAN
happen, but only via two independently-swapped slots converging on the
same replacement exercise — a pre-existing swap-system edge case, not
something Task 2 introduces. Proposal: a REPLACE prescription matches by
resolved id, so if convergence has produced two rows with that id, both
get the override (can't disambiguate which one the model meant, and
applying it to only one would be an arbitrary, silent choice). A note is
always emitted either way (see Q4), and when the match count is >1 the
note says so explicitly rather than pretending it was one clean match.

Q2 — dayKey naming a day the current template doesn't generate?
Reject with reason. Matches everything else in this build. New
existence-family check, next to Gate 1/1b: dayKey must be in
getProgram(data).map(d => d.id). Unknown dayKey rejects that one
prescription with the specific reason and the offered id, same shape as
Gate 1's unknown-exerciseId message. Doesn't reject the whole batch —
partial application, same as everywhere else here.

Q3 — Does weeklySetsByGroup count a replaced slot once? Where is that
enforced?
Two separate mechanisms both have to hold:
  - Render side: section 1's in-place splice, not push. A REPLACE never
    grows the array, so t[g] += ex.sets (weeklySetsByGroup's own
    accumulation loop, unchanged) sums the same number of entries it
    always did — the new sets value simply overwrote the old one in the
    array before this loop ran.
  - Gate side (the actual gap the handoff note flagged): applyGated
    Prescriptions's running tally seeds from ctx.weeklyGroupSets (today's
    baseline, pre-this-batch). If an incoming prescription is a REPLACE,
    that baseline number ALREADY INCLUDES the slot it's about to override.
    So before adding addedSets, the tally must first subtract that slot's
    current contribution: runningGroupSets[group] -= existingSlot.sets.
    buildGateContext needs to expose a lookup
    (ctx.currentSlotFor(dayKey, exerciseId)) built from the SAME section-1
    resolver, used by both the render splice-vs-push decision and this
    gate-side subtraction — one predicate, not two that can drift apart.
  - New edge case this surfaces: two prescriptions in the same batch
    targeting the same (dayKey, exerciseId). The subtraction above assumes
    one baseline value per slot; a second prescription hitting the same
    slot would subtract it a second time from an already-adjusted tally.
    Proposal: reject the second one outright — "a prescription for X on
    this day was already applied earlier in this same plan" — rather than
    let it silently double-subtract or silently last-write-win.

Q4 — Swap vs. prescription, same slot: which wins, and is it visible?
User's instinct (swap wins) holds, and the code doesn't have to fight it —
because matching is defined against the RESOLVED post-swap id (section 2),
the two cases fall out cleanly with no special-casing:
  - Prescription names the pre-swap id (model doesn't know about the swap,
    or the swap happened after the checkin brief was generated) -> that id
    isn't in the day's current output anymore -> ADD, a second exercise
    appears alongside the user's swap. It never reverts the swap, because
    reconciliation only READS data.swaps (via resolveSlot), it never
    writes to it — there's no code path from a prescription to data.swaps
    at all.
  - Prescription names the post-swap id (checkin-tier data already shows
    Claude post-swap ids — confirmed in checkInExerciseIds, 1151) -> that's
    a legitimate parameter override of the exercise that's actually there.
    Not a re-swap, just sets/reps/load on the current identity.
So: user swaps always win on IDENTITY, unconditionally and structurally,
not by a rule that has to be trusted. Addition: every reconciled
prescription gets a note (not just collisions) stating whether it replaced
an existing slot or added a new one — so a case where the model INTENDED
an override but got an ADD because of a stale/pre-swap id is visible in
prescriptionNotes, not silently reinterpreted.

Q5 — Prescriptions across a template switch?
Since dayKey values are template-namespaced (upperA/lowerA... vs
ufUpperA/ufArms... vs shPush/shLower...) and Q2's gate only checks dayKey
validity at apply time, prescriptions already stored from a different
template become inert automatically the next time they'd be read —
section 1's resolver just never finds a matching dayKey in the new
template's day list. Retained-but-inert happens with zero extra code.
What's missing is the visible note: propose a small StalePrescriptions
Notice component following the exact pattern already used for
ClinicianReviewNotice / PainEscalationNotice / InjuryMigrationNotice in
WorkoutFlow (2377-2381) — computed as
(data.plan.prescriptions||[]).filter(p => !currentDayIds.has(p.dayKey)),
shown when non-empty, naming the count and the template mismatch.

Q6 — Order of operations vs. bonus lifts and the trim?
Reconciliation before the trim, as instinct suggested. Concretely, inside
the new section-1 resolver: generator slots -> bonusForDay -> reconcile
prescriptions against that combined list (a REPLACE can target a bonus
lift too, consistent with checkInExerciseIds already including bonus ids
in scope) -> THEN, outside the resolver, per-caller deload scaling ->
fitDayToTime/Gate 7 trim. trimPriority/orderByFocus from sessionRules
still need to be threaded into fitDayToTime's prio() function to become
real (today they're hardcoded focusBoost/isCompound — the sibling fix
sessionRules wiring requires, section 4), but that's about HOW the trim
ranks candidates, not WHEN it runs relative to reconciliation.

================================================================================
4. sessionRules HAS TO GET WIRED AT THE SAME TIME
================================================================================

Not something that can be deferred past this proposal — Gate 6/7's
behavior depends on it, and it's currently silently dropped. Needs: added
to KNOWN_PLAN_KEYS, stored on data.plan.sessionRules (same
wholesale-replace-on-each-apply semantics as prescriptions, for
consistency), and read from data.plan.sessionRules (not just the one
in-flight `gated` object) on every future buildGateContext call —
otherwise caps configured by an earlier paste vanish the moment you view a
different screen.

================================================================================
5. LEGS-CAP HEADROOM (handoff item 2) — CONFIRMED FIXED BY ITEM 3, NOT SEPARATE
================================================================================

defaultGroupCap = max(mav, baseline) stays as-is — still correct for a
pure ADD against a group already over its mav. What changes is that a
REPLACE no longer inflates the "baseline" it's compared against, because
section 3's subtraction step nets out the replaced slot before the new
value is added. So a prescription that swaps one leg exercise's sets down
while adding another up gets evaluated against real headroom, not phantom
headroom created by double-counting the same slot. No separate code path
needed once section 3 exists.

RESOLUTIONS (user review round 2)
================================================================================

All four open decisions APPROVED as proposed:
  1. Gate 8 double-deload — fix it: deload scaling becomes render-time-only,
     stored prescriptions hold raw values. This is a correct revision to
     Task 4's signed-off behavior, not a regression — record it as an
     amendment in DEFERRED-TESTS.md when it lands (commit 3). Add an
     assertion that a stored prescription's load is never a deload-scaled
     value, so it can't silently re-stack later.
  2. dayKey required on every prescription, not optional. Reject a
     prescription missing dayKey with a specific reason.
  3. Five-call-site consolidation done as its own commit before any
     reconciliation logic, with a byte-identical-output assertion so a
     refactor regression is bisectable separately from a behavior
     regression. DONE — see "COMMIT 1" below. One correction surfaced
     during implementation: DayPicker.lastDone is NOT actually one of the
     duplicated call sites. Its inline logic omits both `focus` and bonus
     lifts (day.exercises.map(slot => resolveSlot(slot, data.swaps).id),
     no bonusForDay call at all) — narrower semantics than the other four,
     kept deliberately (folding bonus lifts into "last done" would widen
     what counts as done, an unrequested behavior change). So the
     consolidation is 4 call sites (DayPage, weeklySetsByGroup,
     dayFittedMinutes, dayFocusSummary) into resolveDayExercises();
     DayPicker.lastDone stays its own untouched one-liner.
  4. StalePrescriptionsNotice — build following the existing notice
     pattern (ClinicianReviewNotice / PainEscalationNotice /
     InjuryMigrationNotice in WorkoutFlow).

Three conditions, all accepted as stated:
  A. Q1's "apply to both duplicates" reversed to REJECT instead, naming
     the ambiguity and both slot ids. Conservative failure on the rare
     convergent-swap edge case, consistent with the build's own governing
     principle.
  B. Q3's within-batch collision: "first" means array order (the order
     `rec.prescriptions` arrives in). The rejection message for the
     second (and any further) prescription targeting the same
     (dayKey, exerciseId) pair names which one was kept.
  C. sessionRules persistence — DECIDED: MERGE with existing
     data.plan.sessionRules, not wholesale replace. Diverges from the
     user's stated lean; reasoning below.

     Prescriptions and sessionRules aren't actually analogous the way
     "consistency" suggests. A prescriptions array is a full snapshot —
     "this is the complete set of overrides for right now" — so wholesale
     replacement each paste is correct by construction. weeklyGroupSetCaps
     is different in kind: a standing safety-adjacent limit, not a
     per-paste instruction. A lightweight checkin-tier paste has no reason
     to restate caps it isn't touching (checkin tier's whole design point,
     per TASK-5-FIXES-REVIEW.txt, is a smaller payload that doesn't
     re-prompt for things like this) — and it would be actively bad if
     omitting them, for that reason alone, silently reverted a
     previously-tightened cap to the looser default the next time any
     plan gets applied.

     Mechanics: shallow-merge sessionRules' own top-level keys
     (maxSetsPerMovement, orderByFocus, trimPriority) — a key present in
     the new paste overwrites; a key absent falls through to what was
     already stored. weeklyGroupSetCaps gets a nested per-group merge
     specifically (the safety-critical piece): a new paste's cap for
     "shoulders" doesn't erase an existing cap for "legs". A key present
     in the new paste always wins outright — the model can still
     loosen/tighten any specific cap; it just can't blank out ones it
     didn't mention.

     This satisfies "loud, not a line item" differently than proposed:
     since omission causes no change under merge, there's nothing to
     announce on omission. What's loud instead is a note on actual change
     — "cap updated: shoulders 20 -> 24" style — surfaced whenever a
     merge actually alters a stored value, which is the case that matters
     more than a reset-that-didn't-happen would have been.

     Explicit clearing of a cap (setting it back to "no cap") isn't
     supported by this — a real gap, but not one this build needs solved:
     no test case or observed failure calls for it, and it's addable
     later (an explicit null/removal sentinel) without disturbing this
     shape.

TWO QUESTIONS BEFORE COMMIT 3 (user review round 3)
================================================================================

Q1 — DayPicker.lastDone: does "done" hold against a list a prescription can
now change?

Answer: it needed to change, and now does. Before commit 3, resolveDayExercises
had no reconciliation logic at all, so lastDone's exclusion was moot — there
was nothing for it to miss yet. Once commit 3 lands, a prescription can ADD an
exercise that isn't in day.exercises at all; if the user logged THAT exercise
and nothing else on the day, the static list would report "not started" even
though the user did do the day's coach-authored work — stale relative to what
this app now actually prescribes, which is the specific kind of mismatch this
whole build exists to close (Task 5 fixed an analogous case: lifts visible in
Insights but absent from the exported brief).

Fix: lastDone now calls resolveDayExercises(day, data) and filters out
isBonus entries, rather than reading day.exercises directly. This required NO
change to resolveDayExercises's contract — every entry already carries
isBonus (bonusForDay sets it true; generator slots and reconciled entries
both leave it falsy), so lastDone just filters on data already present.
Bonus lifts stay excluded, unchanged from before: they're ambient and
focus-slider-driven, not the stable "what is this day" a deliberate,
gate-approved prescription is — folding them in would still be an
unrequested widening, just via a different call site than the one originally
flagged.

Verified (scripts/check-prescription-reconciliation.js): a session logged
only against an ADDed exercise now registers as "last done" for that day; a
session logged only against a bonus lift still does not (regression check).
Live headless-browser confirmation: after applying a plan that ADDs "Dips"
to Upper A, the day picker's "last done" — not directly exercised in this
round's browser pass, but covered by the unit test above with the same
underlying function calls DayPicker itself now makes.

Q2 — Condition C: can an existing cap still be explicitly changed or removed,
and does the note fire on change, not just addition?

Changed — confirmed, was already true and already tested (check-session-
rules.js test 3b: legs 18 -> 22 via an explicit re-paste; live-browser
confirmation in commit 2's writeup). A key present in the incoming paste
always overwrites the stored value for that key, merge semantics only
protect keys the paste DIDN'T mention.

Removed — this was a genuine, previously-undocumented gap, now closed. The
per-group merge (`{...existing, ...incoming.weeklyGroupSetCaps}`) was
letting a `null` value pass through as a literal stored `null`, and Gate 6's
own cap lookup (`ctx.weeklyGroupSetCaps[group] ?? defaultGroupCap(...)`)
already treats `null` as nullish and falls through to the default — meaning
explicit removal was ALREADY reachable by accident, just untested and
undocumented (indistinguishable, before this fix, from a bug). Made it a
real, intentional, tested capability: mergeSessionRules now explicitly
deletes a group's key from the stored weeklyGroupSetCaps when the incoming
value for it is `null`, rather than leaving a stray null sitting in
persisted data. Pasting `{"weeklyGroupSetCaps": {"shoulders": null}}` clears
that group's cap back to the default (max(mav, current baseline)).
describeSessionRulesChange now reports a clear back to null as "-> default"
in its note (not a literal "null"), consistent with how the FROM side of an
addition already reads "default" when there was no prior explicit cap.

This isn't "immutable" even without this fix — any explicit numeric value
already overwrote a stored cap. What was missing was specifically "go back
to having no explicit cap at all," which is a real, distinct state
(defaultGroupCap's own baseline-tracking behavior) from "explicit cap set to
some large number." Confirmed via scripts/check-session-rules.js (new
assertions: null clears the key entirely from storage — not stored as
literal null — and produces a "-> default" note; a fresh merge with no
prior state also deletes rather than storing null; clearing a cap that was
never set is a real no-op, no note) and re-verified condition C's "changed"
half still passes unaffected. Also verified this fix actually catches a
regression, not just present: temporarily reverted the delete logic, reran
— 5/22 assertions failed exactly as predicted (literal null values
surfacing in storage, spurious/missing notes), restored, reran clean. Live
headless-browser confirmation: seeded {legs: 18, shoulders: 20}, pasted a
plan clearing only shoulders — UI showed "Session rules updated: Shoulders
weekly cap 20 → default.", storage ended up with exactly {legs: 18}
(shoulders key gone, not null). Zero console errors.
