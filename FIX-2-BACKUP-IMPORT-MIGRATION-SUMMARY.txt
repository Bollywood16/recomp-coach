FIX 2 — SHARED MIGRATION FUNCTION FOR BOOT AND BACKUP-IMPORT PATHS
Branch: task-0-injury-profile
Status: IMPLEMENTED, TESTED, COMMITTED. Part 2 of 3 (Fix 3 not started).

================================================================================
THE BUG
================================================================================

TASK-0-BACKUP-MIGRATION-REVIEW.txt, section 1. There are two "load a
persisted record" code paths: App's boot-time localStorage read, and
BackupCard.importData (the "Import backup" button on the Log tab — the
ONLY way a downloaded backup file ever actually gets back into the app).
Only the boot path ran the goalProfile.injuryRecovery -> recoveringMode
fail-safe migration, the one-time migration notice, the
injuryProfileHistory entry, and the goblet -> boxsquat session rename.
The import path did none of it — it just merged
`incoming.injuryProfile ? merge : (data.injuryProfile || defaults)`,
which never once reads `goalProfile` at all.

Verified live (Playwright, fresh app, real Sept 6 backup) before this fix:
recoveringMode landed on true, but only because the app's already-loaded
default (DEFAULT_INJURY_PROFILE.recoveringMode: true) happened to be true
— not because anything read the file's own goalProfile.injuryRecovery. No
migration notice, no history entry, no goblet rename (all 8 goblet
sessions stayed tagged "goblet"). Had the file's goalProfile.injuryRecovery
been false (gating explicitly turned off), the import would have silently
turned gating ON anyway, with zero notice.

================================================================================
THE FIX
================================================================================

One new function, migrateInjuryAndGobletData(source, existing), called
from both places — no duplicated logic left to drift:

- Boot path (App's load effect): migrateInjuryAndGobletData(found, null).
  `existing` is null; nothing is loaded yet for a record to fall back onto.
- Import path (BackupCard.importData): migrateInjuryAndGobletData(incoming,
  data). `existing` is the app's current in-memory data.

Algorithm is unchanged from what the boot path already did (ported
verbatim, not redesigned) — see the function's own comment in index.html
for the full rationale:

- Whether migration is needed is decided from `source` ALONE, never
  falling back to `existing`. A live app's injuryProfile is always
  truthy (DEFAULT_INJURY_PROFILE), so folding `existing` into that check
  would make the fail-safe permanently unreachable on import — restoring
  an old backup means loading THAT backup's own history, not silently
  inheriting whatever the current device happens to have in memory.
- `existing` is consulted only for the bookkeeping fallbacks
  (injuryProfileHistory, an already-resolved gobletBoxSquatMigration) when
  `source` doesn't carry its own — so re-importing an old file after the
  goblet/boxsquat prompt was already resolved on this device does not
  re-trigger it.
- Fail-safe polarity, confirmed with you directly (2026-09-20) before
  writing any assertions, since my first read of the ported logic
  produced the OPPOSITE of what your Fix 2 request literally described:
  a real, explicit goalProfile.injuryRecovery === false is honored as OFF
  (a confirmed prior user choice — the Task 0 grep found it was only ever
  written by a manual toggle click, never an automated override).
  Absent/null/anything-else-falsy fails safe to ON. Your call: the bug
  was the import path's SILENCE, never the polarity — overriding an
  explicit false on every import would make the toggle effectively
  un-turn-offable, which is its own silent failure. The notice now fires
  in BOTH directions (recoveringMode landing true OR false), which is the
  actual fix.
- Goblet -> boxsquat rename happens IN PLACE within the single `sessions`
  array (there's only one) — same ids, same sets, only exerciseId changes.
  No separate per-id bucket exists for weeklySeries/bestSet/stallScore to
  disagree about, so e1RM trend and stall detection see one continuous
  history under the new id post-rename, never a split one. Confirmed
  directly: weeklySeries(sessions, "boxsquat") computed AFTER migration is
  byte-identical to weeklySeries(sessions, "goblet") computed on the
  ORIGINAL file BEFORE migration.
