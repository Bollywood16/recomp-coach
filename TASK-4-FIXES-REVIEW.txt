ITEM 2 — Escalation clearance defined
================================================================================
isPainEscalating rewritten to walk the full session history in
chronological order rather than only inspecting a snapshot of the last 4
— "currently escalating" is a question about the sequence since the last
trigger, which a snapshot can't answer correctly once a trigger has fired
and later sessions come in.

Clearance: 3 CONSECUTIVE sessions with an answered pain value at or below
threshold. Dismissed/unanswered sessions hold the streak (skipped
entirely — neither advance nor reset it, matching your instruction
exactly). An answered over-threshold value resets the streak to 0.

Clearance is logged to injuryProfileHistory via a transition-detecting
useEffect in PainEscalationNotice (comparing this render's escalating-cats
set to the previous one via useRef) — kept out of isPainEscalating itself,
which stays a pure, side-effect-free read, callable from both the gate
context builder and the notice component without double-logging.

Verified the full state machine: escalating right after trigger; still
escalating after 1 and 2 clean answered sessions; clears exactly at the
3rd; a dismissed session in the middle holds (neither advances nor
resets); an answered high-pain session resets the streak to 0; recovers
correctly after a reset given 2 more clean sessions (still escalating,
correctly not yet cleared).

================================================================================
Written into the comment above isPainEscalating, one sentence: among the
last 4 sessions for a pattern, if >=3 have an answered pain value,
escalation triggers when the most recent answered value is >=2 points
above the oldest answered value in that window. Labeled explicitly as "AN
EXPLICITLY CHOSEN HEURISTIC WITH NO CLINICAL BASIS, deliberately biased to
over-trigger rather than under-trigger" in the comment itself.

Verified: 3 answered sessions rising 0->1->2 (all under threshold) still
triggers via the trend rule alone; flat 1->1->1 does not.

ITEM 4 — Allowlist pick replaces delete-based denylist
================================================================================
applyCoachGates no longer does `{ ...rec, gates: [] }` at all. It now
starts from `{ gates: [] }` and copies only KNOWN_PLAN_KEYS (template,
focus, sessionMin, calorieDelta, prescriptions, pushback, assessment,
nutritionNote, nextCheckIn) off `rec`. Anything else `rec` contains is
dropped and surfaced as a gates[] message: "Ignored unrecognized field(s)
in the pasted plan: X, Y." — the delete-based scrub from the last round is
gone entirely, superseded by this.

check-write-isolation.js retargeted: asserts (a) no `...rec` spread
pattern exists anywhere in applyCoachGates's body, and (b) injuryProfile
is never present in the KNOWN_PLAN_KEYS list. Sanity-tested both failure
modes by injecting each violation into a scratch copy of the file and
confirming the checker fails loudly on each, then confirmed the real
source passes.

Verified: a pasted plan with both an attacker-supplied injuryProfile key
and a benign unrecognized field produces gated.injuryProfile === undefined
AND a gates[] message naming both fields explicitly; known fields (e.g.
sessionMin, calorieDelta) still apply normally alongside the message.

ITEM 5 — Gate 6 default cap decided
================================================================================
defaultGroupCap(group, weeklyGroupSets) = max(MUSCLE_GROUPS[group].mav,
weeklyGroupSets[group] || 0) — never below the live program's own current
baseline for that group.

What this does and doesn't fix, made explicit rather than implied: for a
group already at/above mav (legs: baseline ~26 vs mav 20), the cap is now
26, so the rejection reason cites an honest number instead of one already
violated by the unmodified baseline alone — but there's still no headroom
above baseline for that group, since the running tally also starts from
baseline. Verified this directly: a 1-set legext addition is still
rejected, but the reason now says "above the 26-set cap" (correct, matches
the actual sustainable ceiling for that group) rather than the old,
already-violated 20. A group with real headroom below mav (arms) is
unaffected — a 1-set curl addition passes exactly as before.

Documented as a residual, acknowledged limitation in DEFERRED-TESTS.md:
full resolution needs Task 2 to teach the generator that a prescription
can REPLACE a baseline-counted exercise's sets rather than only ever
adding to them — Task 4 has no such concept yet.

================================================================================
ITEM 6 — Escalation grouping limitation documented, not rebuilt
================================================================================
Added to DEFERRED-TESTS.md and to PainEscalationNotice's own displayed
copy (verified live in the browser screenshot): grouping by `cat` is both
too wide (any pain on one lift suppresses/tightens every lift sharing
that cat) and too narrow (a hip labral issue spans both the squat and
hinge cats, which this treats as two unrelated patterns, so neither alone
may reach the 2-of-4 trigger) — under-detecting exactly the injury this
app was built around. Flagged for whoever next touches the escalation
gate; not rebuilt now, per your instruction.
