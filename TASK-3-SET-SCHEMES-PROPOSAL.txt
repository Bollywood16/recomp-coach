TASK 3 — SET SCHEMES (BACK-OFF AND DROP SETS): DESIGN PROPOSAL
Branch: task-0-injury-profile
Status: PROPOSAL — reviewed with user, not yet implemented. No logger code
written against this yet.

Scope per the build spec:

  {"type":"straight"}
  {"type":"backoff","topSets":2,"backoffSets":2,"backoffLoadPct":80}
    — accepts backoffLoad (absolute lb) as an alternative to the percentage
  {"type":"drop","drops":1,"dropPct":20,"appliesTo":"lastSet"}
    — appliesTo: "lastSet" | "allSets"

Requirements from the spec:
  1. The logger records each segment as its own set row with its own actual
     load. The e1RM engine and stall detector must not be corrupted by
     drop-set segments.
  2. Drop segments are EXCLUDED from weekly hard-set volume counts but
     INCLUDED in fatigue tracking. Document the decision where it can't be
     re-decided wrongly.
  3. Session card renders schemes legibly:
     "2 x 15 @ 12.5 lb, then 2 x 15 @ 10 lb"
  4. Duration estimation accounts for schemes when fitting to sessionMin.

Constraints that follow from earlier tasks, checked explicitly:
  5. maxSetsPerMovement: does a back-off scheme's topSets+backoffSets count
     against the cap as one movement's total? Confirm capAndSplitMovement
     sees the scheme's real total, not just a `sets` field.
  6. Gate 3's load sanity runs against the TOP load — verify backoffLoadPct
     can't smuggle a high top load past it.
  7. Gate 8's render-time-only deload scaling — confirm it scales scheme
     segments coherently, not just the top sets.
  8. Pain escalation (Gate 5) is a one-way ratchet toward conservative — on
     an escalating pattern, should drop sets be prescribed at all? User's
     position: no, escalation should strip schemes to straight sets.

Grounding: read resolveDayExercises, resolveSlot, recommend(), bestSet(),
weeklySeries(), weeklySetsByGroup, capAndSplitMovement, gate3LoadSanity,
gate5PainEscalation, isPainEscalating, fitDayToTime, gate7DurationTrim
before writing this. Line numbers below are as of commit b75ae75
(Task 2 commit 4).

================================================================================
DATA MODEL
================================================================================

scheme lives on the resolved exercise (ex.scheme), arriving via
day.exercises[].scheme (generator-authored) or prescriptions[].scheme
(coach-authored, added to resolveDayExercises's existing OVERRIDE_FIELDS
list so REPLACE/ADD reconciliation carries it through exactly like
sets/repMin already do). Shape unchanged from the spec.

Three different "how much" numbers fall out of a scheme, and conflating
them is what would break requirements 1, 2, 4, and 5:

  Number                          | Helper              | straight | backoff              | drop
  ---------------------------------------------------------------------------------------------------------------
  Hard-set count (Gate 6,         | hardSetsFor(ex)      | ex.sets  | topSets+backoffSets  | ex.sets (unaffected)
  maxSetsPerMovement,
  weeklySetsByGroup)
  ---------------------------------------------------------------------------------------------------------------
  Total logged segments           | totalSegmentsFor(ex) | ex.sets  | topSets+backoffSets  | ex.sets + drops *
  (duration, logger pre-fill)     |                      |          |                      | (appliesTo==="allSets"
                                   |                      |          |                      |   ? ex.sets : 1)
  ---------------------------------------------------------------------------------------------------------------
  Tonnage / "fatigue tracking"    | weeklySeries()'s     | already correct unconditionally, no code change needed
                                   | existing .vol field  |

That third row is why requirement 2's "included in fatigue tracking"
needs ZERO code change — weeklySeries already does
s.sets.reduce((a,x)=>a+w*r) over whatever rows exist. The only place that
needs new logic is the hard-set side (hardSetsFor).

Logged session rows gain one field:
  { w, r, segment: "straight" | "top" | "backoff" | "drop" }
Each physical segment (each backoff set, each drop continuation) is its
own row, per requirement 1 — mechanical once totalSegmentsFor tells the
logger how many rows to pre-fill and at what default weight each one
gets (top load, backoffLoad ?? topLoad*backoffLoadPct/100,
topLoad*(1-dropPct/100)).

WHY segment HAS TO EXIST, not just be inferred later from load ratios —
the sharper reason for requirement 1 than e1RM corruption alone:
recommend()'s progression math (index.html:1683-1723) computes
allTop/belowMin/decay from EVERY row in the last session, unfiltered.
That logic already exists specifically to detect "load too heavy, reps
collapsing across sets" and prescribe a backoff — its own note text says
so ("back off rather than grinding"). Feed it a DELIBERATE backoff/drop
session unfiltered and every scheme'd session looks like unintended decay
and triggers a false "Reduce". So:
  - bestSet()/weeklySeries() (e1RM, stall detection): filter out
    segment==="drop" rows before picking the best set. Backoff rows stay
    in — a backoff set's e1RM will essentially never beat the top set's,
    but excluding drops matters because a drop segment can produce an
    inflated Epley estimate from a high-rep, low-weight continuation.
  - recommend()'s double-progression check: filter to
    segment==="top" || segment==="straight" only. "Did every set hit the
    rep ceiling" is a question about the working sets, never the
    deliberately-lighter ones.

================================================================================
POINT 5 — capAndSplitMovement / weeklySetsByGroup
================================================================================

Both currently read ex.sets raw (index.html:1543 in capAndSplitMovement,
index.html:1000 in weeklySetsByGroup's fitted.forEach). Fix: both call
hardSetsFor(ex) instead. For a backoff scheme this means topSets+
backoffSets IS authoritative — if that sums above maxSetsPerMovement, it
gets capped and split exactly like a flat over-cap prescription does
today. For drop, hardSetsFor ignores the scheme entirely, so a drop
scheme can never be used to sneak volume past the cap.

DECISION NEEDING SIGN-OFF: when a capped exercise carries a backoff
scheme, which part gets trimmed first? Proposed: backoffSets down to 0,
then topSets — mirrors the existing "protect the prioritized work" trim
philosophy. Does the SPAWNED pool-mate ever inherit a scheme, or does
overflow always render as a plain straight set? Proposed: always
straight — the overflow is leftover volume, not a deliberate intensity
choice.

================================================================================
POINT 6 — Gate 3 vs backoff/drop load smuggling
================================================================================

Gate 3 (index.html:1989-2027) only ever inspects prescription.load — the
top load. Two live smuggling vectors on top of that check:
  - scheme.backoffLoad (absolute) is never validated against anything.
  - scheme.backoffLoadPct > 100 makes the "backoff" heavier than the
    already-approved top — backward, and an unchecked increase riding on
    a field nothing looks at.

Fix: not a new rejecting gate (a derived-from-an-approved-number question
isn't a safety judgment call, it's arithmetic) — a small clamp step run
AFTER gates 3/4/5 finalize value.load, so a Gate-4 pain reduction or
Gate-5 escalation cap on the top automatically cascades: clamp
backoffLoadPct to <=100; if scheme.backoffLoad exceeds the final top
load, replace it with the percentage-derived value and note it. One
place enforces "no segment ever exceeds the scheme's own top load,"
rather than every consumer needing to remember to check it. Proposed
name: clampSchemeToTopLoad(value), called at the tail of
runPrescriptionGates.

================================================================================
POINT 7 — Gate 8 render-time deload, scheme-coherent
================================================================================

Two parts:
  - Load: fine for free IF backoff/drop loads are always derived at
    render time from the (already deload-scaled) top load rather than
    cached as a stale absolute number — the same clamp function from
    point 6 handles this, since it re-derives from whatever value.load
    currently is.
  - Sets: DayPage's isDeload block only touches .sets today.

A DECISION SURFACED ALONGSIDE POINT 8, NOT DECIDED SILENTLY: should
deload also strip schemes to straight — same logic as escalation,
arguably stronger, since deload is a blanket whole-program recovery week
and drop sets are specifically an effort-to-failure-maximizing technique
that works against that. Proposed: yes. Implementation: one line added
to DayPage's existing isDeload block (scheme: {type:"straight"}
alongside its existing sets reduction) — bolted onto the mechanism that
already exists rather than a new one, so recommend(), session-card
rendering, and duration estimation never need to know deload is active;
they just never see a non-straight scheme that week.

================================================================================
POINT 8 — escalation strips schemes to straight
================================================================================

Agreed with the user's position. Implemented as an extension of
gate5PainEscalation (index.html:2064-2076): whenever
ctx.escalatingCats.has(ex.cat), force value.scheme = {type:"straight"}
alongside its existing sets-cap. Documented in the "ESCALATION IS A
ONE-WAY RATCHET" comment block that already governs gates 3/4/5, so this
can't be re-inverted without deleting the comment that explains why —
same treatment as the rest of that ratchet.

A THIRD INTERACTION FOUND WHILE TRACING THIS, not asked for but real:
gate5PainEscalation's lastSetCount = last.sets.length (index.html:2068)
counts raw logged rows. Once drop segments are separate rows, a
4-hard-set session with one drop logs as 5 rows — the escalation cap
would silently admit 5 "sets" next time instead of capping at the true
4. Needs to become a hard-set row count (segment !== "drop"), not
.length. Same corruption class as the e1RM concern in requirement 1,
just a third place it was hiding.

================================================================================
ALSO FOUND: DURATION (POINT 4) HAS ITS OWN TRIM-ORDER WRINKLE
================================================================================

fitDayToTime and gate7DurationTrim share the same
dur = sets*(40+restSec) shape. Backoff needs no formula change (its sets
are already full rested sets once hardSetsFor/totalSegmentsFor agree).
Drop needs an additive term — proposing a DROP_SEGMENT_SEC constant
(~20s: no independent rest, since minimal/no rest is the defining trait
of a drop set, just enough added work time). This number has no spec
anchor the way DEFAULT_MAX_SETS_PER_MOVEMENT did — flagged as arbitrary
and open to adjustment. Separately, trimming a scheme'd exercise for
time should shave in the order: drop segments first (cheapest, don't
count as hard sets anyway), then backoffSets, then top/straight sets —
same priority ordering as point 5's cap-trim, for the same reason.

================================================================================
RECAP — DECISIONS NEEDING SIGN-OFF BEFORE IMPLEMENTATION
================================================================================

1. Backoff's topSets+backoffSets is authoritative for hard-set count,
   overriding any separately-specified sets field, rather than requiring
   them to match / erroring if they disagree.
2. Overflow trim order within a capped backoff scheme: backoffSets first,
   then topSets; spawned pool-mate always gets a plain straight scheme.
3. The "no segment exceeds the top load" clamp is a silent, unconditional
   derivation step (not a rejecting gate) — always fixes rather than
   flags for user confirmation, matching gates 3/4/5's existing "modify
   and continue" pattern.
4. Deload strips schemes to straight, same as escalation (point 8's logic
   extended).
5. Drop-segment duration cost: proposing ~20s work, no independent rest —
   flagging since there's no existing anchor value like
   DEFAULT_MAX_SETS_PER_MOVEMENT had.
6. Gate 5's lastSetCount needs to switch from raw row count to hard-set
   row count.

================================================================================
RESOLUTIONS (user review round 2)
================================================================================

All six decisions APPROVED, with three changes and two additions:

1. Backoff-total authoritative — APPROVED WITH CHANGE. Reject a
   prescription whose bare `sets` field disagrees with its backoff
   scheme's own topSets+backoffSets, rather than silently preferring one.
   Implemented as Gate 1e (gate1eSchemeConsistency).
2. Trim order + spawned-always-straight — APPROVED as proposed.
3. Clamp, not a rejecting gate — APPROVED WITH CHANGE. Always emit a note,
   never silent, same as every other modify-and-continue path. A
   backoffLoadPct over 100 especially — that's an author writing something
   incoherent, not arithmetic drift, and it must be visible.
4. Deload strips schemes to straight — APPROVED as proposed. Reasoning
   noted as stronger than the escalation case (point 8): deload is a
   blanket recovery week, drop sets are an effort-maximizing technique.
5. DROP_SEGMENT_SEC ~20s — APPROVED as a named constant with a comment
   stating it's an estimate with no research or spec anchor.
6. lastSetCount -> hard-set row count — APPROVED, recorded as a Task 4
   sign-off amendment in DEFERRED-TESTS.md (second one, alongside Gate 8's).

Two additions:
  A. Migration default: absent `segment` reads as "straight," never
     "drop." Every filter must use EXCLUSION predicates (`!== "drop"`,
     `!== "backoff" && !== "drop"`), never INCLUSION whitelists
     (`=== "top"`) — an inclusion whitelist silently excludes every
     pre-Task-3 session, since `undefined === "top"` is false. This
     corrected a mistake in my own first-draft proposal text, which said
     "filter to segment==='top'||'straight'" — exactly the wrong form.
  B. Partial logging: confirmed saveSession's existing `.filter(r>0)`
     already prevents phantom zero-rep rows (unchanged, out of scope this
     round). A manually-added extra row gets no explicit segment tag,
     which is safe under the exclusion-predicate design (undefined reads
     as straight) — to be made explicit when the logger UI ships.

Also requested: grep every consumer of a session's set rows before
implementing, since four were found one at a time. Full audit below.

SET-ROW CONSUMER AUDIT (requested before implementation)

Correctness-critical (code changed):
  1. bestSet() (e1RM/weeklySeries/stallScore) — excludes "drop".
  2. recommend()'s progression math — excludes "backoff" and "drop"
     (THE finding: unfiltered, a deliberate backoff/drop reads as
     unintended decay, compounding a reduction on top of a reduction).
  3. gate5PainEscalation's lastSetCount — excludes "drop" (decision 6).
  4. buildCoachBrief's <set_quality> section — sent to the coaching LLM
     with an instruction to flag rep decay as "too heavy, don't repeat."
     Unfiltered, a deliberate backoff/drop reads to the MODEL exactly
     like the collapse it's told to flag. Annotated inline
     ("80x12(backoff)"), not filtered — the model should see the whole
     session, correctly labeled.

Correctness-adjacent, minor (code changed):
  5. ExerciseCard's "LAST TIME" panel — colored a row orange when
     s.r < ex.repMin. A backoff/drop segment is deliberately at a
     different rep target; unfiltered, this flags correct execution as a
     shortfall. Now skips the warning for backoff/drop rows.

Confirmed safe by construction, no change needed (stated explicitly
rather than silently assumed):
  6. lastWorkingWeight() — Math.max over the session's weights. A
     backoff/drop segment is by definition <= the top load once the
     clamp (decision 3) holds that invariant structurally, so Math.max
     can never select one.
  7. weeklySeries's tonnage sum (.vol) — deliberately unfiltered; this IS
     "fatigue tracking" per requirement 2.

Display-only, no corruption risk, deferred to the logger-UI round for
legible formatting (requirement 3):
  8. Log tab's "Recent sessions" list.
  9. ExerciseCard's own draft input array — the write side, requirement
     1's implementation surface itself, not a historical consumer.
